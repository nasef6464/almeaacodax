# ALMEAA — خطة المدرب، معلم المدرسة، ومدير المدرسة

> الحالة: `APPROVED FOR IMPLEMENTATION / NO RUNTIME CHANGE YET`
> المصدر: الكود الحالي وخطة School OS + Smart Classroom المعتمدة.
> سجل الأهداف: `ACCOUNT_WORKSPACES_GOALS_AR.md` (`G7–G12`).

## 1. القرار المنتجى

لا نبني نظام مستخدمين جديدًا ولا نغيّر حسابات المستخدمين القديمة. يبقى `User`
واحدًا، لكن تظهر له **مساحة عمل** واضحة بحسب الصلاحية والسياق:

| الشخصية الظاهرة | الهوية التقنية | النطاق | ما لا تملكه |
|---|---|---|---|
| مدير المنصة | `admin` | المنصة كلها | لا قيود مدرسة |
| مدرب منصة | `teacher` + `managedPathIds` / `managedSubjectIds` | مساراته ومواده فقط | المدارس والفصول غير المسندة |
| معلم مدرسة | `teacher` + `SchoolMembership(role=teacher)` + `TeachingAssignment` | مدرسته وفصوله المكلّف بها | محتوى منصة أو مدرسة أخرى |
| مدير مدرسة | **`school_admin` جديد** + عضويات وصلاحيات مدارس صريحة | إحصاءات مدارسه وإضافة الطلاب ونقلهم داخل المدرسة | العقود وإعدادات المنصة وأي عملية غير مفوّضة صراحةً |
| مشرف مدرسة | `supervisor` | متابعة تشغيلية بحسب المدرسة/الفصل | إعدادات المنصة والعقود |

الحساب الهجين ممكن: نفس المستخدم قد يكون مدرب منصة ومعلم مدرسة، لكنه يختار
صراحةً `مساحة المدرب` أو `مساحة المدرسة`؛ لا تجمع الواجهتان الأدوات في صفحة واحدة.

## 2. اللوحات النهائية

1. **لوحة مدير المنصة**: مدارس، عقود، مدربون، محتوى عام، إعدادات المنصة.
2. **لوحة مدرب المنصة** (`/instructor-dashboard`): دورات ودروس وأسئلة واختبارات
   ضمن المسارات والمواد المسندة فقط. كل إنشاء أو تعديل يمر بتحقق خادمي للنطاق.
3. **لوحة معلم المدرسة** (`/school-teacher-dashboard`): الفصول المكلف بها،
   الاختبارات المدرسية، وTeacher Control Console للحصص الذكية.
4. **لوحة مدير المدرسة** (`/school-director-dashboard`): نظرة تنفيذية على مدارسه
   ومساحة محدودة لإدارة الطلاب. يستطيع إضافة طالب ونقله بين فصول المدرسة، وتظهر
   له أدوات أخرى فقط عندما يفوضها مدير المنصة. تبدأ التقارير مجمعة، ولا تظهر
   البيانات الفردية إلا في عملية مصرح بها تحتاجها فعلًا.
5. **لوحة المشرف**: المتابعة التشغيلية والتقارير والتدخلات ضمن نطاقه.

## 3. التنفيذ بالترتيب

### T1 — هوية المدرب ومساحة المدرب

- أبق `teacher` في قاعدة البيانات للتوافق؛ الاسم الظاهر في مساحة المحتوى هو
  `مدرب منصة`.
- أنشئ route ولوحة مستقلة للمدرب، ولا تستخدم لوحة الإدارة العامة.
- راجع كل كتابة للمحتوى: Course، Lesson، Question، Quiz، Library؛ أضف تحقق
  خادمي موحّد أن `pathId` أو `subjectId` داخل نطاق المدرب.
- المدرب يرسل المحتوى للمراجعة؛ مدير المنصة وحده يعتمد/ينشر عندما تتطلب السياسة.
- لا تسمح للمدرب بقراءة أو تعديل محتوى مدرب آخر خارج النطاق.

**دليل القبول:** مدرب الكمي يستطيع إنشاء سؤال/درس/دورة كمي فقط؛ محاولة كتابة
لفظي أو تحصيلي ترجع `403`، والواجهة لا تعرض الاختيارات الخارجة عن نطاقه.

### T2 — معلم المدرسة ومساحة المدرسة

- حافظ على `SchoolMembership(role=teacher)` و`TeachingAssignment` الحاليين.
- أنشئ `/school-teacher-dashboard` يعرض فقط فصول المعلم وتكليفاته.
- انقل روابط Smart Classroom وSchool Assessments إلى هذه المساحة؛ لا تعطها
إنشاء محتوى منصة أو إدارة مدرسة.

**دليل القبول:** المعلم A لا يرى فصل B ولا يستطيع بدء Smart Class أو توجيه
اختبار إليه.

### D1 — مدير المدرسة: role وعضوية آمنة

- أضف `school_admin` إلى enums في backend/frontend و`SchoolMembership` فقط.
- أضف إلى كل عضوية مدير مدرسة `permissions` من allowlist خادمية ثابتة؛ لا تجعل
  الصلاحيات عامة على المستخدم لأن المدير قد يملك صلاحيات مختلفة في كل مدرسة.
- لا تضف `tenantId` ولا نظام حسابات موازٍ.
- مدير المنصة ينشئ الحساب ويربطه بمدرسة أو أكثر عبر `SchoolMembership` صريحة؛
  يكون `User.schoolId` مجرد fallback للتوافق، وليس مصدر صلاحية متعدد المدارس.
- أضف في لوحة مدير المنصة إدارة ربط المدارس ومصفوفة الصلاحيات، مع حفظ فعلي
  وaudit log لكل منح أو سحب.
- كل route لمدير المدرسة يبدأ بـ`requireRole(['school_admin'])` ثم يحل
  memberships النشطة والصلاحية المطلوبة من الخادم؛ لا يكفي إخفاء زر في الواجهة.

صلاحيات العضوية الأساسية:

- `SCHOOL_OVERVIEW_VIEW`
- `SCHOOL_REPORTS_AGGREGATE_VIEW`
- `SCHOOL_STUDENTS_VIEW`
- `SCHOOL_STUDENTS_ADD`
- `SCHOOL_STUDENTS_MOVE_CLASS`

صلاحيات إضافية يستطيع مدير المنصة منحها لكل مدرسة على حدة:

- `SCHOOL_STUDENTS_UPDATE_BASIC`
- `SCHOOL_STUDENTS_DEACTIVATE` — تعطيل قابل للاسترجاع، وليس حذفًا نهائيًا.
- `SCHOOL_CLASSES_MANAGE`
- `SCHOOL_TEACHERS_ASSIGN`
- `SCHOOL_REPORTS_DETAILED_VIEW`
- `SCHOOL_REPORTS_EXPORT`
- `SCHOOL_ASSESSMENTS_MANAGE`
- `SCHOOL_SMART_CLASSROOM_VIEW`
- `SCHOOL_INTERVENTIONS_VIEW`
- `SCHOOL_INTERVENTIONS_MANAGE`
- `SCHOOL_STUDENTS_TRANSFER_SCHOOL` — استثناء للنقل بين مدرستين يديرهما الحساب.

يمكن للواجهة عرض قوالب مثل `إدارة أساسية` و`تقارير موسعة` و`تشغيل أكاديمي`
و`مخصص`، لكنها تحفظ دائمًا الصلاحيات الصريحة؛ القالب ليس مصدر الصلاحية. ولا تظهر
صلاحية اختيارية في لوحة المنصة قبل اكتمال الـAPI والواجهة والاختبارات الخاصة بها.

**دليل القبول:** مدير مدرسة A لا يستطيع طلب أو تخمين بيانات مدرسة B؛ حساب بلا
عضوية فعالة يرجع `403`، وسحب صلاحية منه يجعل العملية ترجع `403` فورًا.

### D2 — لوحة مدير المدرسة: إحصاءات وإدارة طلاب مفوّضة

- أضف `GET /api/school-director/overview` للإحصاءات المجمعة.
- يعيد aggregates للمدارس المصرح بها: عدد الفصول، الطلاب، المعلمين، المشرفين،
  محاولات ومتوسط الاختبارات المدرسية، وجلسات Smart Classroom المكتملة.
- أضف `GET /api/school-director/students?schoolId=...` بقائمة محدودة يحتاجها
  المدير للإضافة والنقل، من دون answer keys أو بيانات تعليمية غير لازمة.
- أضف `POST /api/school-director/students` لإضافة طالب إلى مدرسة وفصل مصرحين.
  لا يقبل إنشاء موظف أو مدير، ويتحقق من هوية الطالب والبريد ومنع الاستحواذ الصامت
  على طالب مرتبط بمدرسة أخرى.
- أضف `PATCH /api/school-director/students/:id/class` لنقل الطالب بين فصول
  المدرسة نفسها. يجب أن تكون العملية atomic وidempotent وتحدّث ارتباطات المجموعات
  الحالية من خلال service واحدة مع audit log.
- لا تضف delete endpoint. النقل بين مدرستين ليس جزءًا من الصلاحية الأساسية؛ يضاف
  لاحقًا فقط مع `SCHOOL_STUDENTS_TRANSFER_SCHOOL` وعضويتين فعالتين للمصدر والهدف
  وتأكيد خادمي وسجل تدقيق.
- صفحة `/school-director-dashboard` مستقلة، مع اختيار مدرسة إن كان الحساب
  مرتبطًا بأكثر من مدرسة، وقسم `إدارة الطلاب` للإضافة والنقل، وأقسام اختيارية
  تظهر فقط حسب صلاحيات المدرسة المحددة.
- أعد استخدام خدمات إنشاء المستخدم وربط `SCHOOL` / `CLASS` الحالية خلف façade
  خاص بمدير المدرسة؛ لا تكرر نماذج الطلاب أو منطق العضوية.

**دليل القبول:** لوحة منفصلة وأرقام مجمعة صحيحة؛ مدير مدرسة A يضيف طالبًا وينقله
بين فصول A، لكنه لا يضيفه أو ينقله إلى B، ولا يحذف طالبًا، ولا يرى أدوات إضافية
من دون التفويض المقابل.

### D3 — التقارير والـUX والانتقال

- سمّ بوضوح: `مدرب منصة`، `معلم مدرسة`، `مدير مدرسة`؛ لا تستخدم كلمة "معلم"
  وحدها في شاشات الإدارة.
- أضف badges وفلاتر حسب مساحة العمل، لا حسب تخمين من اسم المستخدم.
- الحساب الهجين يحصل على context switch واضح؛ يحفظ اختيار السياق في URL/local
  state ولا يرفع صلاحياته.
- حدّث export المستخدمين ليذكر نوع المساحة والارتباطات الفعلية.

## 4. حدود غير قابلة للتفاوض

- لا role migration كبيرة أو تعديل جماعي للحسابات الحالية.
- لا تغيير في scoring أو `QuizResult` أو الدفع أو البيانات التاريخية.
- لا CRUD عام لمدير المدرسة: الكتابة الأساسية محصورة في إضافة طالب ونقله داخل
  مدرسته، وباقي العمليات تتطلب capability خادمية صريحة لكل مدرسة.
- لا hard delete للطلاب، ولا نقل بين المدارس افتراضيًا.
- مدير المنصة فقط يستطيع منح صلاحيات مدير المدرسة أو سحبها.
- لا دمج Analytics المدرسة مع Platform Learning في رقم واحد.
- لا microservices أو global `tenantId` أو Video/WebRTC داخلي.

## 5. الاختبارات المطلوبة لكل PR

1. Typecheck + production build.
2. Contract tests للـRBAC: مدير مدرسة A ضد مدرسة B، مدرب كمي ضد مادة غير
   مسندة، ومعلم مدرسة ضد فصل غير مكلّف به.
3. API tests: overview لا يعيد PII، وإضافة الطالب لا تنشئ staff، والنقل داخل
   المدرسة يحدّث كل الارتباطات مرة واحدة حتى عند تكرار الطلب.
4. اختبارات مدير المدرسة: يستطيع الإضافة والنقل داخل A، ولا يستطيع الإضافة إلى B
   أو النقل إليها أو الحذف أو منح نفسه صلاحية.
5. اختبر أن الصلاحية الاختيارية تعمل عند منحها، وترجع `403` فور سحبها، وأن النقل
   بين المدارس يتطلب الصلاحية الخاصة وعضويتين فعالتين معًا.
6. UI smoke: كل role يصل للوحة الصحيحة فقط، والأدوات غير المفوضة لا تظهر.
7. اختبر account hybrid في السياقين مع عدم تسرب أدوات أحدهما إلى الآخر.
8. تحقق من audit log لإضافة الطالب ونقله ومنح الصلاحيات وسحبها.
9. CI على commit التنفيذ بالضبط، ثم تحديث `CODEX_EXECUTION_STATE.md` وخرائط
   البيانات فقط إذا تغيرت الملكية أو query responsibility فعليًا.
