# دليل بيئة المراجعة والتأهيل (ALMEAA — Staging Review Guide)

---

## 1. الغرض من بيئة Staging
تتيح بيئة **Staging** لمالك المنصة وفريق الجودة اختبار أحدث التغييرات والميزات المكتملة على الفرع المصدري الفعلي دون الحاجة إلى دمجها إلى فرع الإنتاج (`main`) قبل اعتمادها النهائي.

يحل هذا الإجراء مشكلتين جوهريتين:
1. اختبار الميزات ورحلات المستخدمين على بيئة سحابية حقيقية مطابقة للواقع.
2. تفادي الدمج المبكر إلى `main` وحماية استقرار الإنتاج.

---

| العنصر | الرابط / القيمة | الغرض |
| :--- | :--- | :--- |

## 3. طريقة عمل الاتصال والتوثيق في Staging
- **الاتصال عبر نفس النطاق (Same-Origin `/api`)**:
  - يتصل المتصفح بـ `https://<staging-domain>/api/...`
  - يقوم وكيل Vercel (`vercel.json`) بتوجيه الطلب تلقائياً إلى خادم الـ Backend على Render.
  - ملفات الارتباط (Cookies) تُسجل كـ First-Party على نطاق Staging نفسه دون حظر من المتصفحات.
  - لا توجد أخطاء CORS لأن الاتصال يتم على نفس النطاق.
- **تسجيل الدخول المعتمد للمراجعة**:
  - يتم حصراً عبر **البريد الإلكتروني وكلمة المرور (Email/Password)** أو رقم الهوية / الجوال.
  - خاصية Google OAuth مؤجلة لبيئة Staging لأنها تعيد التوجيه صلبياً لنطاق الإنتاج من إعدادات مزود الخدمة.

---

## 4. كيفية التأكد أنك داخل بيئة Staging
1. **شريط العنوان في المتصفح**: يتضمن اسم نطاق Staging ولا يحتوي على `almeaacodax.vercel.app`.
2. **شارة STAGING في الهيدر**: تظهر شارة برتقالية صغيرة وواضحة بجوار الشعار في الهيدر العلوي بنص `STAGING`.
3. **عدم مغادرة النطاق**: كافة عمليات التنقل (`Dashboard`، `Quiz`، `Results`، `Learning`) تتم عبر مسارات داخلية في React Router دون تغيير النطاق.

## 5. خطوات مراجعة أدوار المستخدمين (Role Review Steps)

> [!NOTE]
> لا تُستخدم بيانات حقيقية أو سرية داخل هذا التوثيق. تُستخدم حسابات الاختبار المعتمدة في البيئة المعزولة.

### أ. رحلة الطالب (Student Journey)
1. افتح رابط Staging.
2. اضغط "تسجيل الدخول" وأدخل بريد وكلمة مرور حساب الطالب التجريبي.
3. تحقق من التوجيه التلقائي إلى لوحة تحكم الطالب (`/dashboard`).
4. افتح المحتوى التعليمي (`Learning Space`).
5. ابدأ حلاً لاختبار أو تدريب (`Quiz Runner`) وتأكد من تنظيم الشاشة، المؤقت، وشارات الخيارات (أ، ب، ج، د).
6. أنهِ الاختبار وراجع شاشة النتائج (`Results`)، مراجعة الأسئلة وتصفية الأخطاء، ونافذة تحليل المهارات.
7. اضغط Refresh في أي صفحة وتأكد من بقاء الجلسة ونفس النطاق دون الخروج للإنتاج.

### ب. رحلة المشرف الأكاديمي (Supervisor Journey)
1. سجل الدخول بحساب المشرف الأكاديمي التجريبي.
2. تحقق من الوصول المباشر للوحة المشرف (`/supervisor-dashboard`).
3. عاين الطلاب التابعين لنطاق الإشراف، الفصول المخصصة، والتقارير المتاحة.
4. تأكد من ثبات النطاق وبقاء الجلسة بعد التحديث.

### ج. رحلة مدير النظام (Admin Journey)
1. سجل الدخول بحساب مدير النظام (Admin).
2. تحقق من الوصول للوحة التحكم الشاملة (`/admin-dashboard`).
3. عاين تبويبات إدارة المدارس، بنك الأسئلة، والاختبارات المركزية.
4. تأكد من ثبات النطاق وبقاء الجلسة.

---

## 6. كيفية تحديث بيئة Staging
1. العمل والتعديل يتم حصراً على الفرع:
   ```bash
   git checkout codex/assessment-data-evolution
   ```
2. تنفيذ التعديل واختبارات الجودة محلياً (`npm run typecheck`, `npm run build`, smokes).
3. الرفع إلى نفس الفرع:
   ```bash
   git push origin codex/assessment-data-evolution
   ```
4. يقوم Vercel ببناء ونشر الكوميت الجديد تلقائياً على بيئة Staging فور اكتمال الـ Push.

---

## 7. القواعد الصارمة والسياسات الدائمة (Permanent Rules)

> [!IMPORTANT]
> 1. **ممنوع الدمج التلقائي إلى `main`**: لا يتم عمل Merge أو PR إلى `main` إلا بعد مراجعة واعتماد مالك المشروع لكافة الـ Product Gates المقفلة.
> 2. **بيئة Staging ليست إنتاجاً**: لا تحتوي على معاملات مالية حقيقية ولا تُرسل إشعارات لأولياء أمور حقيقيين.
> 3. **سرية البيانات**: ممنوع إدراج كلمات المرور، المفاتيح السرية (API Keys)، أو الرموز المميزة (Tokens) في أي ملف داخل Git.
