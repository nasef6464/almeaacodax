# ALMEAA — تدقيق جاهزية الإطلاق التشغيلي (L0)

**تاريخ التدقيق:** 2026-09-08
**نطاق التدقيق:** الإطلاق التشغيلي الآمن فقط: التطابق بين Git والنشر، الصحة، الدخول، النسخ الاحتياطي، المراقبة، ووصفة VPS.
**خارج النطاق:** لا تغيير في المنتج أو الأدوار أو التقييم أو الدفع أو بيانات الإنتاج.

## القرار التنفيذي

المنصة **صالحة لاستكمال تجهيز إطلاق تجريبي محدود بعد معالجة البنود الحرجة أدناه**، لكنها ليست جاهزة بعد لنقل DNS أو استقبال مدارس مدفوعة على VPS. السبب ليس نقصًا في وحدات المنتج؛ السبب أن أدلة التشغيل بعد النشر والنسخ الاحتياطي والاستعادة لم تكتمل.

- صحة API الحي في Render كانت `200` عند commit `02208c210c3c`، مع MongoDB وRedis للـrate limit والـqueue في حالة ready.

## REAL GAPS

### Critical — دليل التشغيل بعد النشر غير صالح

آخر تشغيلات `Post Deploy Smoke` فشلت لأن اعتماد المشرف في GitHub أعاد `401 Authentication required`. هذا ليس فشلًا في اختبار المنتج، لكنه يلغي الدليل الآلي لرحلات الإنتاج بعد كل نشر.

**الإجراء:** أنشئ حساب مشرف تشغيل مخصصًا بأقل صلاحية مطلوبة، وحدّث GitHub Secrets بوسيلة صالحة (`SMOKE_ADMIN_TOKEN` قصير العمر أو بيانات الحساب المخصصة)، ثم شغّل الـworkflow مرة واحدة. لا تستخدم حساب المالك ولا تضع أي سر في Git أو المحادثة.

### Critical — النسخ الاحتياطي والاستعادة ليسا جاهزين للتشغيل اليومي

السكربتات الحالية تنفذ dump/restore يدويًا فقط؛ لا يوجد جدول يومي، تخزين خارج الـVPS، سياسة احتفاظ، ولا تمرين استعادة إلى قاعدة منفصلة.

**الإجراء:** فعّل Atlas Backup/PITR المتاح في باقتك، مع نسخة يومية مشفرة خارج الـVPS، وسياسة احتفاظ مكتوبة، وتمرين استعادة شهري إلى قاعدة staging. لا تُجرّب `--drop` على قاعدة الإنتاج.

### Critical — لا يوجد نشر متطابق مثبت للـHEAD الحالي

الخادم الحي عند `02208c210c3c` بينما `main` عند `c2b4d296...` وقت التدقيق.

**الإجراء:** انشر commit محددًا إلى بيئة staging أولًا، ثم تحقق من `/api/health` (حقل commit) و`/api/health/ready`، وبعدها انشر نفس الـartifact إلى VPS/production. لا تعتمد على «آخر نشر» دون مطابقة SHA.

## PARTIAL

- Sentry موجود اختياريًا في الكود، لكن `SENTRY_DSN` والإشعار الفعلي من الإنتاج غير مثبتين.
- وصفة VPS تتضمن rollback يدويًا؛ لا يوجد بعد artifact release مرقّم أو اختبار rollback حي.
- البريد/تأكيد الحساب موجودان في الكود، لكن وصول رسالة حقيقية من مزود بريد production غير مثبت.
- واجهة Vercel تستخدم HSTS، بينما تحقق CSP على الواجهة غير مثبت في هذا التدقيق. API يعيد Helmet headers.

## BLOCKED

- إعداد أسرار GitHub الصحيحة واختبار smoke التشغيلي: يتطلب إجراء مالك المشروع في GitHub.
- اختيار مزود النسخة الاحتياطية الخارجية، إعداد Atlas PITR، وموفر البريد وSentry: قرارات وحسابات تشغيلية لا يجوز افتراضها أو إنشاؤها تلقائيًا.
- لا يتم نقل DNS أو نشر VPS نهائيًا قبل إغلاق البنود الحرجة.

## دليل التشغيل الحي — 2026-09-08

بعد إصلاح Workflow الفحص ليستخدم أسرار حساب المدير الموجودة في المستودع من دون كشف قيمها، نجح فحص الإنتاج في تسجيل الدخول للحسابات: المدير، المعلم، المشرف، الطالب، الطالب المستفيد من باقة، وولي الأمر. كما نجحت 68 من 71 قراءة تشغيلية على API الحي.

البنود الثلاثة غير المثبتة ليست فشل تسجيل أو فشل صلاحية عامة:

- سجل الاختبار التجريبي المعلّق ذي المعرف الثابت `quiz_seed_pending_review` غير موجود في البيانات الحية؛ لذلك لا يمكن إثبات ظهوره للمراجع والمالك من ذلك السجل بالذات.
- نطاق المشرف الحي لا يعيد طلابًا ذوي ضعف (`weakestStudents=0`) في بياناته الحالية؛ لذلك لا يثبت هذا الفحص بطاقة «الطلاب الذين يحتاجون دعمًا» بمثال حي.

**التصنيف:** `NOT PROVEN / DATA FIXTURE`، وليس دليلًا على إتاحة المحتوى للطالب أو على انهيار مسار تسجيل الدخول. لا تُنشأ بيانات اختبار في production لهذا الغرض. يغلق الدليل في staging أو Pilot بمشرف وفصل وطالب ونتيجة اختبار مخصصة، ثم يعاد فحص المسار كاملًا.

## STRONG MVP للإطلاق التجريبي

الحد الأدنى لمدرسة تجريبية واحدة هو:

1. نشر API وواجهة من نفس commit مثبت.
2. نطاقان تحت نفس النطاق الرئيسي: `app.<domain>` و`api.<domain>` لتقليل مخاطر third-party cookies.
3. MongoDB managed مع backup/PITR واستعادة مثبتة على staging.
4. Redis managed أو Redis VPS مراقب للـrate limiting والـqueue.
5. Sentry + مراقبة uptime للـ`/api/health/ready` وتنبيه لبريد المالك.
6. نجاح Post Deploy Smoke بحساب تشغيل منفصل، ثم مرور الرحلات الخمس يدويًا: مدير، مشرف، معلم، طالب، ولي أمر.

## DEFERRED

- multi-region، microservices، data warehouse، event platform، وتوسيع أفقي متقدم.
- نماذج AI جديدة؛ ليست شرطًا لإطلاق المنصة، ويجب ألا تصبح جزءًا من scoring أو قرار تعليمي حاسم قبل إثبات الاستخدام.
- تحسينات UI إضافية غير مرتبطة بالاستقرار أو رحلة الدخول.
- تحديثات الحزم المتوسطة: تُنفذ في دفعة dependency maintenance منفصلة مع CI كامل.

## ترتيب التنفيذ المعتمد

1. **L0-01 — تشغيل post-deploy smoke صالح:** المالك يضع اعتماد تشغيل مخصصًا في GitHub Secrets؛ ثم نجاح workflow على commit مطابق للنشر.
2. **L0-02 — Staging/VPS deployment proof:** إعداد VPS والنطاقين وبيئة staging، نشر SHA محدد، والتحقق من الصحة والـrollback.
3. **L0-03 — Backup/restore drill:** Atlas/PITR + نسخة خارجية + استعادة إلى staging وتسجيل الزمن والنتيجة.
4. **L0-04 — Auth/email/monitoring proof:** بريد تأكيد واستعادة فعليان، Sentry event، وuptime alert.
5. **L0-05 — Pilot acceptance:** خمسة أدوار، مدرسة وفصل وطالب موجّه واختبار ونتيجة، دون استخدام حساب المالك كحساب smoke.

## أثر التغيير

- لا تغيّر على API أو RBAC أو scoring أو payments أو schema أو بيانات الإنتاج.
- هذا التقرير ليس دليل production cutover؛ إنه قائمة الأدلة المطلوبة قبل ذلك.
