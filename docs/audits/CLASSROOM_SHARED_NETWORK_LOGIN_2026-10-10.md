## Observed problem and bounded change

Real trial setup was stopped by the deployed source limit of 20 authentication requests per 15 minutes (429, remaining zero, Retry-After 517 seconds). Correct passwords from classmates shared this budget. Simply skipping successful requests with a source limit of 20 would still reject classmates while their concurrent logins are pending.

Login now has three layers: 60 total requests per source per minute; ten pending/failed attempts per normalized account over the existing auth window (successful responses decrement); and the owner-selected 10/15-minute source budget applied to completed 400/401 login failures. Persisted password locks now use the same owner-selected ten-failure account limit and remain authoritative across identifiers and sources. All login aliases, national ID and phone-password routes receive protection. Register, forgot/reset password, global and sensitive-action policies remain unchanged, as do proxy trust, CSRF, cookies, tokens, RBAC, disabled-account checks and response bodies. Existing explicit admin bypass conditions are preserved; no trial-account exemption was added.

The completed-failure source guard checks before authentication and atomically records failures before returning the rejection. Success does not erase source failures. Requests already admitted before concurrent failures complete remain bounded by the short burst limit; this is not a claim of a hard 10 in-flight cap. A source with 10 completed failures blocks even correct credentials until expiry. Account checks and canonical password locks still protect individual identities.

Reuse the existing rate-limit Redis connection with hashed identifiers/source keys and expiring counters. Lua read and INCR/first-PEXPIRE are atomic; ioredis prefixes the declared EVAL key. No new production service, connection, polling or paid tier. Without configured Redis, fallback memory holds at most 10,000 active source entries; capacity/storage failures fail closed. Redis protection failures never permit a login through the failed guard. No database migration or historical result mutation.
