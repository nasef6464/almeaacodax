## الهدف والحدود
تسليم ALMEAA كمنتج تعليمي يمكن فهمه وصيانته واختباره من أي مطور/Agent جديد، مع حزمة إثبات لكل رحلة حساسة، ودون إعادة بناء واسعة أو ضغط على خدمات مجانية أو كتابة بيانات إنتاج. **لا يمكن الجزم بفحص كل زر أو ملف إلا بعد مطابقة جرد آلي بأدلة تنفيذ مقابلة.**
المعيار هو إصدار آمن قابل للإطلاق وفق بوابة #298، لا إلغاء كل تحسينات P2/P3.

## توزيع المسؤولية ومنع التعارض
- مراجع الجودة GPT: المسح المعماري، خريطة الوظائف، تحليل الأثر بين المجالات، قراءة CI والتحقق المستقل، Issues وأدلة التسليم.
- Codex/Sol: يتولى إصلاح **رحلة مستقلة يحددها المالك** فقط عند التسليم، ولا يعدل الملفات نفسها أو schemas مشتركة بالتزامن؛ اقرأ قائمة PRs قبل بدء تعديل.
- جميع تغييرات التطبيق في فرع عمل مختبَر ومملوك لجهة واحدة بعد موافقة المالك. العمل التجريبي في هذا المسار مقيد بالفرع `test/almeaa-isolated-20261008`؛ لا تعديل `main`، ولا merge/production deploy/Atlas/R2/Redis/Render/Vercel.
- عند ظهور تعارض، أوقف الملف المشترك، وحدد مالكًا واحدًا وراجع diff قبل الاستكمال.

- تحديد البيانات الحساسة وقيود الأدوار والعزل بين المدارس وعمليات الكتابة والآثار الجانبية وQueue/Socket/Cache.
- تصنيف P0 فقد بيانات/تسريب/درجات خاطئة/شراء خاطئ/سقوط رحلة أساسية، ثم P1 تعطّل رحلة أو خطأ استعادة مهم، P2 صيانة/تجربة، P3 تجميل.

### المرحلة 1: اختبارات حماية قبل أي تقسيم
- بناء خصائص السلوك الحالي للمسارات الحساسة واختبارها بدون تعديل المنتج: identity/auth, school isolation, quiz autosave/resume, once-only submit, grading, immutable result, access-code consumption, entitlement, classroom batch lifecycle.
- اختبار حالات السماح والمنع، الطلبات المكررة، الانقطاع والتأخير، وإعادة المحاولة. استخدم isolated fixtures/Mongo وBrowser عند السماح، لا بيانات إنتاج.
- اجتياز مسارات الحماية الفعلية قبل تغيير المكونات؛ لا تعتمد على static string checks وحدها.
**الخروج:** لكل ملف عالي الخطورة اختبار baseline أحمر/أخضر أو ثبوت وجود فحوص سلوك سابقة موثقة.

### المرحلة 2: هيكلة محددة تستحق التكلفة

**الخروج:** ملف/وحدة واضحة الملكية، لا تغيّر في API/persistence/permissions/grades بالصدفة، وإثبات عدم التراجع.

### المرحلة 3: فحص الرحلات الكاملة بتغطية مترابطة
ترتيب أولي حسب أثر الطالب:
1. الطالب: دخول → اختيار اختبار/أسئلة → حفظ إجابات تلقائيًا → خروج/عودة → استئناف → تسليم مرة واحدة → حساب درجة من الخادم → تقرير/خطأ → مراجعة وتدريب علاجي → تحديث إتقان.
2. الفصل المباشر: مدرس/طالب/انتظار → إعداد حزمة → إرسال/نشر → اتصال/reconnect → إجابة/إنهاء دفعة → تقرير/إغلاق؛ مع الخصوصية وحالات تأخر التحديث.
3. المدرسة/الفصل/الصلاحيات: تمييز admin/director/supervisor/teacher/student/parent؛ عزل مدرسة A عن B ومشاركة الطلاب/حذف مدارس وعلاقات عضوية.
4. الاشتراك والدفع والكود: مدرسة/باقة/كود/صلاحية/حجز idempotent وحالات إعادة المحاولة/الرفض.
5. بنك الأسئلة والمحتوى والإتقان/التقارير والذكاء الاصطناعي والوسائط/صوت/سبورة.
كل رحلة تختبر زرًا/سلوكًا وظيفيًا + handler + API + RBAC + DB + mobile/RTL + loading/empty/error + مسارات الخصوصية + cross-domain regression.
**الخروج:** سجل لكل اختبار PASS/FAIL/NOT TESTED/BLOCKED مع الأدلة المربوطة بالـSHA.
